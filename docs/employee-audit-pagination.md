# Phase 2 increment AZ: full authorised employee change history

Prerequisites: immutable Core HR audit/request journal, current employee/field access policy, AY's evidenced legacy latest-100 limit. All45 source IDs remain in scope. SH-05 is partial across modules; HR-01 and SH-01 apply. This increment covers generic employee-change events only; lifecycle/module-specific journals remain separate.

Workflow: self, current authorised manager or HR opens an employee profile → Change history, filters by authorised field/action, selects newest/oldest recorded order, and navigates/refreshes without losing the profile. Counts and rows exclude inaccessible fields **before** pagination; no public total leaks private events. Preserve UTC recording instant separately from business-effective date, actor, reason, old/new values and correlation ID. No bulk edits or export claim.

Architecture: GET `/api/v1/employees/{id}/change-history` → thin web/cursor adapter → EmployeeHistoryUseCases → application current-record/field policy → application-owned EmployeeHistoryStore → Core HR-owned JDBC audit/request projection. A bounded repeatable-read transaction provides internally consistent watermark/count/page. Framework-free input/output models; configuration owns Clock/transaction wiring. V65 adds a selection index only; no record rewrite or new dependency. The old array endpoint `/history` retains its documented latest100 contract and is deprecated in favour of the new page API.

Navigation: keyset `(recorded_at,id)` with exact decimal ID strings avoids timestamp ties and JavaScript integer loss. First read chooses a maximum eligible audit ID; later pages use that boundary and an anchor. The bounded base64url cursor is navigation state, **not authorisation**, with identity/tenant/employee/role/field/filter/order/size fingerprint and a verified scoped anchor. Forging it never widens server-derived read scope. No secret/new identity provider dependency. Role/filter/record mismatch requires refresh. Previous navigation is a local cursor stack; refresh resets the boundary.

Consistency: immutable committed rows present at the first read can be traversed without duplicate/shift from later higher-ID writes. This is not an MVCC snapshot across requests: a transaction that reserved a lower ID before the boundary can commit later; it may appear after the current anchor or require refresh if its position was passed. Counts describe currently committed authorised rows within the boundary. No exactly-once export/audit snapshot claim. Each next/previous read rechecks current reporting scope and field policy; no sensitive client persistence/shared caching.

Acceptance / exit evidence:

1. Retrieve every authorised row beyond100, including the earlier birth-date history retained by AY; no missing/duplicate committed fixture IDs across pages or tied timestamps. Exact scoped totals, oldest/newest sorting and field/action filters work with page sizes1–50. Empty results and invalid/malformed/foreign/stale cursor/filter/size input are handled safely.
2. Current self/HR access includes private fields; manager counts/options/rows exclude them before pagination. Other employee/tenant/former manager and forged role/tenant hints are denied. Recheck each page; anchor/token cannot grant access. New writes above the boundary appear only after refresh; document lower-ID late-commit semantics.
3. Profile uses real page API with loading/empty/error/focused retry, keyboard controls, private field-aware choices and mobile wrapping. Changing filter/order/size or employee/version/identity context resets navigation; obsolete requests abort and cannot replace a different profile/page. Preserve independent employment history loading/recovery. Existing changes remain immutable.
4. Execute domain/application/architecture and actual PostgreSQL tests, live strict contracts, browser/axe/mobile/visual checks, retained-data V64→65 digest comparison and isolated restore/recovered API across all supported local roles. Preserve failures/findings, update traceability/checkpoint and measured NFR scope. Do not claim complete SH-05, Phase2 or production readiness.

Provisional NFRs remain unchanged; bounded reads/index are workload protections, not latency/capacity measurements. No new statutory, financial, deletion or retention policy. Next: remaining Core HR organisation/lifecycle/benefits and governed reference/consumer gaps; all later phases/release gates remain open.
