# Phase 3 — attendance and timesheets

Prerequisites: BK/V69; current Core HR identity, record access, effective employment and architecture tests. TS-01 and TS-02 plus SH-01/02/03/05/06/09 are assigned here. Core HR Phase2 remains partial; user explicitly prioritised attendance/timesheets now. TS-03/04, DS-02, later payroll/talent/ERP and all45 source IDs remain in scope.

## Reversible policies and architecture

Timekeeping is a separate hexagonal module. Its application ports obtain current workforce scope through a published Core HR contract; no cross-module table/internal access. Its domain validates attendance intervals and timesheet transitions. PostgreSQL/Flyway owns attendance, sheets, immutable audit, idempotency receipts and actual approved labor-hours costing allocations. The hours ledger is a real persistent allocation/reconciliation capability, not a payroll response or financial posting mock; rates, monetary project costs and payroll consumption remain Phase4/6.

Self-service clock-in/out uses the server UTC instant and an explicit IANA zone. At most one open shift; detect missing checkout and shifts over24h. Corrections create a missed interval or amend an existing shift with exact revision/reason, retain original snapshots, prohibit overlaps and future instants, and validate explicit timestamp offsets against the zone (including DST gaps/folds). Corrections are immediately recorded by the employee, not separately approved; manager/HR independently reviews submitted working hours. No statutory break/overtime/rounding rule is assumed.

One Monday–Sunday sheet per employee/week. Seven date-specific entries, whole minutes0–1440/day, with a supplied activity/cost code for positive time; future/pre-employment positive entries forbidden. Hours entry converts exactly to whole minutes on the backend. Employee saves Draft, submits a nonempty sheet, and tracks status. Rejected sheets can be revised/resubmitted; Submitted/Approved sheets cannot be edited. Current same-tenant manager or HR independently approves/rejects with comment/revision/impact; self and alternate identity self-review denied. Approved sheets are immutable and atomically create one immutable hours allocation per positive day, unique source/day, with exact reconciliation. Retries must not duplicate punches, decisions or allocations. No live payment or public release.

3. Actual approved-hours ledger reconciles sheet total, survives restart and duplicate/concurrent review, never posts rejected/pending time. Expose scoped allocations and immutable audit; no claim of payroll or monetary accounting.
4. Responsive self-service, scoped approval inbox, persistent labels, focused errors/preserved values, unsaved-change protection, consequential approval impact, cancellation/stale-response handling, no optimistic financial/approval state. Real browser journeys, keyboard/axe/mobile inspection.
5. Automated pure-domain, architecture/negative fixture, actual PostgreSQL, API contract and E2E tests. Typecheck/lint/build and existing Java regressions. Retained-data migrations; no historical SQL rewrite. Evidence and45-ID traceability updated; release remains NOT READY until external policy and security/load/recovery gates pass.

Read requests are bounded/paginated; read transactions repeatable and writes serialised per schema/tenant/employee with ten-second transaction limits. Offset pages are not a multi-request snapshot. Attendance and timesheet hours remain independent records: attendance is supporting evidence, not an automatic payable-hours rule. Reviewer may reject discrepancies. User-supplied activity codes are labels, not verified project/account references; monetary costing requires later authoritative mapping.

## Implementation contracts and remaining policy decisions

`TimeUseCases` owns attendance, correction, draft/save, submission/review, scoped detail and complete history. `TimeStore` owns only timekeeping tables. `TimeWorkforce` is implemented through published `corehr.api.TimeWorkforceAccess`; scope is revalidated inside transaction boundaries. Review scope excludes the employee and all immutable prior draft/submission contributor subjects, including after subject reassignment. Changes of tenant, employee or employment episode while awaiting a write lock require reload. Manager queue enumeration is bounded at10,000 visible employees and fails visibly above that threshold; HR uses a tenant predicate directly. No truncated scope is used.

Hours API values must convert exactly to whole minutes. The editor uses integer minutes, so every individual minute is representable without decimal-hour rounding. Submitted/approved snapshots are frozen. Attendance and sheet corrections retain snapshots at UTC microsecond precision; explicit higher-precision correction timestamps are rejected. Approval posts daily labor-minute units synchronously in the same transaction and checks their total. A deferred database reconciliation constraint and immutable source/day keys protect the ledger independently.

Deployment decisions remain open: legal working-time/break policies, permissible correction window and independent correction-review policy, cost-code validation against real projects/cost centres, monetary rates, legal payroll rules, and archival/hold retention periods. All writes currently require the current active/on-leave employment episode; pending sheets from an earlier or ended episode require future governed reconciliation rather than silently applying old hours. Staff currently record their own time; proxy entry, bulk imports, attendance-device ingestion, paid-break classification and final-pay integration are not represented as delivered features. These additions do not remove any TS-01/02 source behaviour; policy limitations and later dependencies remain visible in traceability.

Timekeeping records, command receipts and audit are retained; no generic deletion or truncation is exposed. Privacy/legal-hold policy and production retention require accountable configuration. API queries are tenant-bound, current-scope checked and never accept a tenant header as authority. Existing CSRF/session/security-header/rate/body controls apply. No GPS, biometrics, credentials, bank details or real employee fixtures were added.

The source baseline says approved time transfers to **payroll or costing**. This delivery implements the actual costing-hours path. The traceability inventory had decomposed those alternatives into separate TS-02-B02 payroll and TS-02-B03 costing criteria; both IDs are retained. B02 remains explicitly scheduled for Phase4 rather than being silently deleted or marked complete. No source-ID completion claim hides the remaining payroll consumer.

Command replay authorisation includes the stored result's employee and employment episode, not only tenant/subject/key. This is checked before returning old clock, correction or sheet snapshots. Actual PostgreSQL tests cover same-subject employee reassignment as well as review independence. The remaining replay is a read of an originally recorded outcome, not permission to recreate or re-post it.

## BN: supplied detailed baseline, weekly dashboard, copy and reports

The detailed user baseline is now 28 FE + 32 BE source requirements with 203 decomposed acceptance checks in [timesheet-requirements.md](timesheet-requirements.md) and its JSON source. These supplement the original 45 ERP requirements; the historical 35 TSM rows are retained. None of the full detailed source IDs is signed off as complete.

The `My week` tab reads `/api/v1/time/dashboard?week=YYYY-MM-DD`: own current-episode sheet, actual period controls and current independent review count across all weeks. It never infers missing expected hours from an unconfigured schedule. Reminders are visible workflow/policy context, not delivered notifications.

An owner can copy a recorded source revision through `POST /api/v1/time/sheets/copy` (`sourceId`, `sourceVersion`, later Monday `week`, `reason`, `idempotencyKey`). This creates a DRAFT only, keeps the source unchanged, preserves weekday minutes/activity labels/time zone, revalidates employment dates and target policy, refuses an existing target, and records immutable provenance/receipt. Same-key concurrent requests return the same draft. Copied time is never submitted or allocated automatically. This is duration copying, not effective assignment eligibility or schedule autofill.

`GET /api/v1/time/reports` accepts inclusive reporting Mondays `from`/`through`, optional `employeeId`, and status (default ALL). It resolves identity/tenant and current HR/team scope server-side. Ordinary workers get their own records only; a filter for an unauthorised worker is denied. Totals are over the entire matching result, not the displayed ten-row page. Reports reject ranges over 53 weeks and results over 1,000 sheets instead of silently truncating. Minutes and posted hours are real timekeeping records; monetary costs, overtime, payroll and billing status are absent and explicitly labelled.

`POST /api/v1/time/reports/export` accepts the same JSON filters with CSRF, rechecks permissions and current data, and returns `{filename,content,rows}`. CSV cells are quoted and formula-neutralised. The browser downloads the generated CSV; export preparation is audited with actor, correlation, filters and aggregate counts, without putting employee rows in logs. Repeating export prepares and audits a fresh download, so it may differ if authorised records changed. There is no payment or posting side effect.

Migration V75 adds the tenant/week reporting index without rewriting historical snapshots. Flyway applies it on API startup. No new credentials or environment variables are required. The existing local database, private storage, OIDC/local authentication and application transaction conventions remain in use. Do not edit V70–V74 or remove old test schemas.

Remaining engineering: effective assignments and split entries, categories/templates, break conversion, schedules/holiday/absence, configured overtime/rates, delegated/multistage routing, threaded comments/attachments/declarations, notification jobs, imports, supplier/buyer access, governed processed-time adjustments, payroll/billing consumers and reconciliation. These are missing application capabilities, not all credential blockers. Live Fieldglass/Workday connections additionally need verified interfaces, credentials, mappings and agreed ownership; none is simulated as completed.
