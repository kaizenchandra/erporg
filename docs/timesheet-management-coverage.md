## Existing system and implementation decisions

Next.js16.4/React19.3 strict TypeScript; existing primitives, CSS tokens, client API/session handling and Playwright/axe. Java21/Spring Boot4.0.8; PostgreSQL18.6 with Flyway; CSRF-protected session/OIDC capability. Keep the capability-oriented hexagonal monolith: pure time-policy domain; application access checks/orchestration/ports; thin web and parameterised JDBC adapters; outer transaction composition. Reuse the published Core HR workforce contract for identity, current episode and authorised scope. No direct cross-module table access.

Existing timekeeping already supports persisted seven-day weekly drafts, exact minutes, attendance intervals and corrections, explicit IANA zones/DST checks, individual approval/rejection, immutable audit/receipts, and a reconciled hours costing ledger. Core HR, calendars, documents and notifications exist. Actual project/work-order/task assignment, supplier identity, absence, payroll and billing modules do not yet provide usable timekeeping contracts. Activity codes are labels, not validated project or accounting identities. Existing document permissions concern employee documents and cannot safely be reused as timesheet-attachment permissions.

The current increment adds return/correction/resubmission, pending recall, explicit selected-record atomic bulk review, and weekly HR controls. New V72–V74 migrations preserve old migrations and records. Period controls are appended as immutable revisions, with exact versions, command keys and reasons. The revision checked for each configured save/decision is retained in committed time audit. Current controls govern pending work; revising controls does not recalculate or alter approved historical allocations. Weekly periods remain Monday–Sunday. Maximum1000 control revisions per week is a visible operational safety bound.

An unconfigured week explicitly uses existing local limits:0–1440 whole minutes/day, no submission deadline, recall allowed. HR can configure stricter daily/weekly limits, an absolute deadline, closure and recall permission. Deadline applies to submission, not subsequent manager approval; closure blocks saves/submission/approval. Return/reject and allowed recall may resolve pending records in a closed week. Reopening requires a new HR control revision/reason. Returned time must first be saved as Corrected before resubmission. Existing Rejected→Draft/resubmit behavior is retained for compatibility. No approved-sheet reopening or posted-record edits: adjustment processing is still missing and cannot be represented by recall.

Bulk review affects only checked submissions displayed on the current page, maximum20. The server sorts employee locks, checks every scoped record and exact revision, and performs decisions/allocations/audits/individual receipts plus a whole-selection fingerprint in one transaction. A failure rolls back the entire selection. Retry of the same selection returns recorded outcomes; key reuse for changed selection or decision conflicts. No optimistic approval state.
