## Phase 2 increment A — private contact details
Prerequisites: verified Phase 1 approval/audit/effective-date workflow, current PostgreSQL migrations and scoped APIs. IDs: HR-01 contact/emergency-contact behaviours, HR-03 personal-change submission/status, SH-01 field access, SH-02 independent HR decisions, SH-03 requester status, SH-05 audit. Deliverable: home address and one emergency contact (name, relationship, phone), changeable through the real approval workflow. Address is a bounded free-text local-demo field; structured country-specific addresses, multiple contacts and legal/name identity fields remain scheduled.

Acceptance before implementation: self/HR profile reads show approved current values; future changes do not apply early; invalid phone/blank input yields linked field errors; independent HR approves/rejects; employee self-approval and manager access to private team details are denied. Manager directory/profile payloads redact private values and manager inbox/count/audit paths exclude private requests. Replays/concurrency preserve existing guarantees. Exit evidence requires PostgreSQL/domain/API tests plus a browser submit-to-approval/profile journey and a direct-API privacy test. No source ID or full Phase 2 completion is implied by this increment.

## Phase 2 increment B — department reference workflow
Prerequisites: existing employee/manager scopes, approval/idempotency/audit infrastructure, V5 schema. IDs: HR-02 department hierarchy subset, HR-04 validated department transfers, SH-01 HR-only configuration, SH-05 reference audit, SH-06 effective reference data. Deliverable: create tenant-owned departments with immutable code/name, optional parent, configured cost-centre code, and effective start date; browse current/planned departments; reject unknown/not-yet-effective department transfers at submission and approval. Initial cost-centre mappings are explicitly demonstration values awaiting finance configuration.

Acceptance: HR creates with required reason; replay returns the same record, conflicting replay fails, employee/manager create is denied; parent belongs to the same tenant and is effective by the child's start; self-parent/unknown parent and invalid dates/codes rejected; unique code/name enforced in DB; creation stores actor, UTC recording time, business start date, reason and correlation. UI shows future status and preserves erroneous inputs. An approved department change uses a real reference on its business date. Full positions, hierarchy editing/reorganisation, versioned cost-centre changes and finance costing remain later Phase 2/4 work, not complete HR-02.

## Phase 2 increment C — approved hiring
Prerequisites: department references, independent approval/field policies, PostgreSQL transactions and audit. IDs: HR-01 assigned employee identifiers, HR-05 hiring subset; SH-01 HR access, SH-02 independent review, SH-03 in-app outcome, SH-05 audit, SH-08 durable handoff intent. Deliverable: HR submits a validated hire with configured department, existing same-tenant manager and start date; another HR employee approves/rejects. Approval atomically creates one employee in Onboarding status, records the decision and creates a durable employee-created event awaiting downstream provisioning. New hires do not automatically receive sign-in accounts.

Acceptance: no employee before approval; immutable input snapshot; duplicate submit stable/conflicting replay rejected; self/alternate-identity self approval denied; one concurrent decision winner; no duplicate employee/email on release; wrong-tenant and non-HR reads/writes denied. UI provides submitted/approved/rejected status, decision scope, preserved errors and actual employee profile access after approval. Payroll/access consumers, start-date activation, onboarding completion, rehire, resignation and termination remain explicit later work. No hire-to-payroll completion claim until the real payroll consumer exists. Synthetic second HR reviewer is local only.
